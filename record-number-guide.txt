记录定位说明（csv_cleaner.py 的 trim 流程：空行、空字段与引号内换行）
======================================================================

本文依据仓库根目录当前版本的 csv_cleaner.py，专门解释 trim 清洗流程中
“记录（record）”是如何数出来的：空行、空字段与引号内换行分别怎样影响记录
定位，报错里的 record N 指向哪条记录，以及为什么它不是文本编辑器里的行号。
文中行号对应 csv_cleaner.py 当前源码，可逐条核对。本文只补充说明文档，不
改变程序、参数、摘要结构或既有文档；README 已说明记录序号从表头记为 1，
本文给出能原样复现的完整成功样例、失败样例与边界规则。

一、记录序号是 CSV 记录号，不是物理行号
----------------------------------------

程序从不自己按文本行切分输入，而是把文件交给 Python 标准库 csv 解析器：

* 读取在 read_records()（第 337-357 行）中完成：第 346 行以
  encoding="utf-8-sig"（允许 BOM）、newline="" 只读打开输入；第 347 行用
  csv.reader(infile, delimiter=delimiter, strict=True) 按显式指定的分隔符
  （默认逗号，第 126-127 行、第 367 行）解析，分隔符从不猜测；第 349 行
  `for record_no, record in enumerate(reader, start=1)` 给每条 CSV 记录
  编号，表头是记录 1，其后每条数据记录依次加一。
* csv.reader 理解引号语法：字段可以用双引号包住，引号内的分隔符、转义双
  引号和真实换行都是字段内容。因此一条记录可以横跨多个物理行，记录号只在
  一条完整记录结束时推进一次。引号没闭合等语法错误在 strict=True 下抛
  csv.Error，由第 351-352 行报为 `cannot parse CSV ...`（退出码 2），这
  与后文“列数不符”是两类不同的错误。
* read_records() 的文档字符串（第 338-343 行）明确写出：“Record numbers
  start at 1 for the header; quoted newlines inside a field do not advance
  the number.”

所以报错 `record 5 has 0 field(s), expected 2` 中的 5 是“第 5 条 CSV 记
录（表头算第 1 条）”，不是文件的第 5 个物理行。当某条记录的字段里含有真
实换行时，同一记录会占据多个物理行，两个数字从此错开。

二、从解析、列数校验、单元格清理到输出的顺序
----------------------------------------------

主流程 main()（第 360 行起）对 trim 的处理次序固定，每一步的失败都会在
下一步开始之前终止程序：

1. 路径形参检查（第 423-426 行）：输出不能与输入同路径、输出文件不能已存
   在。这两项在读取输入之前执行，--dry-run 也不例外。
2. 解析全部记录：第 428 行调用 read_records()，得到
   (记录号, 字段列表) 的列表。
3. 表头校验：第 430-431 行，没有任何记录或第一条记录是空列表（0 个字
   段），报 `input is empty: no header record`；其后依次拒绝空列名
   （第 433-434 行）、重名列（第 435-436 行）和找不到目标列
   （第 437-438 行）。注意程序不会跳过开头的空记录去后面寻找表头：第
   430 行只检查 records[0]，第一条是空记录就直接失败。
4. 按记录顺序逐条处理数据（第 447 行 `for record_no, record in
   records[1:]`）：
   * 列数校验在最前面，第 448-450 行：字段数必须等于表头列数
     expected_fields（第 441 行），否则报
     `record N has X field(s), expected Y` 并退出 2。校验先于清理，因此
     一条列数不符的记录不会产生任何清理结果。
   * 单元格清理：第 452 行取目标列的解析后原值 original；第 466 行调用
     规则。trim 就是 str.strip（RULES 表第 251-256 行，第 252 行
     `"trim": str.strip`）：去掉字符串两端空白、保留全部内部空白。
   * 变化判定：第 470 行 `if cleaned != original:` 为真才追加 changes
     （第 471-476 行，before 是解析后原值、after 是清理结果）并把
     changed_cells 加一（第 478 行）。空字符串 strip 后仍是空字符串，
     不变化、不进 changes；纯空白变为空字符串则算一条变化。非目标列从
     不参与比较，原样保留（第 479 行整条记录连同未改动字段一起收入
     out_rows）。
5. 写出（第 482-494 行）：仅当未加 --dry-run 时，第 484 行以 "x" 模式
   （文件必须尚不存在）、encoding="utf-8"（无 BOM）、newline="" 新建输出，
   第 485-486 行用 csv.writer 按输出分隔符写完全部记录。--dry-run 跳过整
   个写出块，不创建文件，也不创建缺失的父目录。
6. 打印摘要（第 496-501 行）：循环与写出都结束后才打印一个 JSON 对象。
   fail()（第 259-261 行）打印 `error: ...` 到标准错误后 sys.exit(2)，任
   何一步失败都到不了第 501 行，因此失败时标准输出必为空，也不存在“先清
   理了一部分、给出部分摘要”的情况。

三、成功样例：trim-records.csv
-------------------------------

把以下内容原样保存为 UTF-8 编码的 trim-records.csv（若当前目录已有同名文
件，请先备份或换到空目录）。全部行尾使用单个 LF；最后一行 `   ,` 之后只
有一个正常的末尾换行。第一行是表头；第一条备注被双引号包住，line one 与
line three 之间是连续两个真实换行（即一个引号内空行）：

    name,note
    " Alice ","line one

    line three"
    ,ok
       ,

三条数据记录（记录号从表头记为 1）的解析结果：

* 记录 2（横跨三个物理行）：name 为两端各一个空格的 ` Alice `；note 的解
  析值为 `line one`、两个连续真实换行、`line three`。
* 记录 3：name 为空字符串（逗号前什么都没有）；note 为 `ok`。
* 记录 4：name 为三个 ASCII 空格；note 为空字符串。

执行导出命令（默认逗号分隔；清理 name 列并开启 --include-changes）：

    python csv_cleaner.py --input trim-records.csv --output cleaned.csv --column name --rule trim --include-changes

结果：退出码 0，标准错误为空，标准输出只有一个 JSON 对象（一行）：

    {"rows": 3, "changed_cells": 2, "changes": [{"record": 2, "column": "name", "before": " Alice ", "after": "Alice"}, {"record": 4, "column": "name", "before": "   ", "after": ""}]}

要点：

* rows 为 3（不含表头），changed_cells 为 2。
* changes 只含记录 2 和 4，按记录顺序排列。记录 2 的 before 保留两端各一
  个空格，after 为 Alice；记录 4 的 before 保留三个 ASCII 空格，after 为
  空字符串。记录 3 的 name 本就是空字符串，str.strip 前后相同，不计数也
  不进 changes；note 列不是目标列，完全不参与比较。
* 引号内那两个连续真实换行属于记录 2 的备注字段：它们让该记录占据三个物
  理行，但记录号只算一条，记录 3、4 的编号不被顶大。

cleaned.csv 被创建，其完整文本如下（展示用；实际文件中每条记录的行尾是
CR+LF，这是 csv.writer 的默认行终止符；记录 2 备注引号内的两个换行保持为
字段内容、仍是 LF；文件为无 BOM 的 UTF-8）：

    name,note
    Alice,"line one

    line three"
    ,ok
    ,

逐字节核对：表头、记录顺序和备注内容均不变——记录 2 的备注仍是 line one
加两个真实换行加 line three，并由 csv.writer 自动重新加上双引号保护；记
录 3 的备注仍为 ok；记录 4 的备注仍为空字符串。变化只有 name 列两处：
` Alice ` 写成 Alice（不再需要引号），三个空格写成空字符串（行首直接是逗
号）。输入 trim-records.csv 以只读方式打开（第 346 行），导出后其字节保
持原样。

四、失败样例：正常末尾换行之后再添一个引号外空行
--------------------------------------------------

把成功样例原封不动保留，仅在文件末尾那个正常换行之后再增加一个空行（即再
多写一个 LF；这个空行在所有引号之外），另存为 trim-records-blank.csv：

    name,note
    " Alice ","line one

    line three"
    ,ok
       ,

    （上面这一行为新增的引号外空行；它与记录 2 备注里那个引号内空行不同）

约定当前目录下不存在 missing 目录。执行 --dry-run，输出路径尚不存在且与
输入不同：

    python csv_cleaner.py --input trim-records-blank.csv --output missing/preview.csv --column name --rule trim --include-changes --dry-run

结果：退出码 2，标准输出为空，标准错误恰好为：

    error: record 5 has 0 field(s), expected 2

运行后 missing 目录与 preview.csv 都不存在，trim-records-blank.csv 字节不
变。

为什么是记录 5：正常的末尾换行只结束记录 4，不产生新记录；而额外的那个
引号外空行向 csv.reader 交出了一条 0 字段的空记录，编号为 5（表头 1、
Alice 记录 2、空 name 记录 3、三个空格记录 4）。第 448-450 行发现它只有
0 个字段、表头要求 2 个，立即失败。

为什么没有部分摘要：即使记录 2 和记录 4 明明有可清理的值，列数校验也发生
在清理与摘要打印之前（第二步在第四步之前，第 448 行先于第 466、501 行），
fail() 直接 sys.exit(2)，JSON 一行都不会打印；--dry-run 下本就没有写出
块，因此也不会留下任何文件。在物理行上，这个空行是文件的第 7 行（记录 2
的引号字段占了第 2 至第 4 行）——这正说明报错数字要按 CSV 记录读，不能当
作编辑器行号。

去掉 --dry-run 做真实导出，报错信息、退出码与“不创建文件”的行为完全相
同：输入校验在写出分支（第 482 行）之前，两种模式同口径。

五、边界规则汇总
----------------

以下规则均可由所标源码位置与本文样例核对：

* 正常末尾换行不增加记录。一个换行只是最后一条记录的终止符；csv.reader 不
  会为它凭空生成一条空记录。成功样例在 `   ,` 之后恰好一个 LF，rows 为
  3，没有记录 5。
* 引号内的空行属于字段，不是记录。成功样例记录 2 备注里两个连续真实换行
  （引号内夹一个空物理行）是 note 字段的内容，记录 2 仍只算一条，记录号
  不在该处推进；清理别的列时，这些换行原样保留、原样写出。
* 单独的逗号表示两个有效空字段。物理上的一行 `,` 在双列表头下解析为两个
  空字符串（["", ""]），字段数为 2，通过第 448 行的列数校验；trim 作用在
  空字符串上不产生变化（changed_cells 为 0），记录正常导出。
* 独立的纯空格行只有一个字段。一行三个 ASCII 空格（不含逗号）解析为
  ["   "]——空格是字段内容，整行就是一个字段，不会被切成两列。在双列表
  头下它列数不符，按第 448-450 行退出 2：
  `error: record 2 has 1 field(s), expected 2`（该行作为紧随表头的唯一
  数据行时记录号为 2）。
* 引号外空行是 0 字段记录，与纯空格行不同。完全空的一行解析为 []（没有
  任何字段，连空字符串字段都没有），在双列表头下报
  `record N has 0 field(s), expected 2`；失败样例中它是记录 5。
* 若首个物理行就在引号外为空，csv.reader 的第一条记录就是 []，第 430-431
  行 `if not records or not records[0][1]:` 为真，报
  `error: input is empty: no header record`。程序只认 records[0] 作表
  头，不会跳过这个空记录去后面寻找真正的表头——即使下一行明明写着
  name,note，它也只会被当成永不处理的记录 2。
* --dry-run 与导出在输入校验上行为相同。两者共用第 428-480 行的读取、表
  头校验、列数校验与清理循环；--dry-run 只跳过第 482-494 行的写出。任何
  输入错误在两种模式下都是退出码 2、标准输出为空、同样的标准错误，且都不
  创建输出文件或目录。--dry-run 同样要求输出路径与输入不同且尚不预先存
  在（第 423-426 行），但不验证父目录是否存在或可写。

六、读到报错时如何定位记录
--------------------------

1. 从 1 开始数：表头恒为记录 1，第一条数据是记录 2；changes 与各报错中的
   record 用同一套编号。
2. 按引号规则数、不按物理行数：遇到起始双引号就一路读到字段闭合，中间的
   换行（包括引号内空行）全部计入当前记录，编号不增加。
3. 区分三种“看起来是空的”行：引号内空行是字段内容；引号外完全空行是
   0 字段记录（列数不符）；只有空格的行是 1 字段记录（列数不符）；带逗号
   的空行按逗号数给出若干个有效空字段。
4. 用解析器核对而不是用行号核对：以 csv.reader 读入文件后枚举
   (enumerate(start=1))，报错里的 N 与枚举下标一一对应；直接用支持 CSV 语
   法的编辑器或一小段 Python 枚举记录，即可看到 record N 的实际字段。

本文所述语义的源码落点：规则表 RULES 中 trim 即 str.strip（第 251-256
行）、fail()（第 259-261 行）、read_records() 与编号枚举（第 337-357
行，关键行 346、347、349、351-352）、路径形参检查（第 423-426 行）、空
表头判定（第 430-431 行）、列数校验（第 447-450 行）、单元格清理与变化
判定（第 452、466、470-480 行）、--dry-run 写出分支（第 482-494 行）、
摘要组装与打印（第 496-501 行）。
